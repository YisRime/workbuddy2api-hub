# WorkBuddy 客户端抓包与上游指纹核对

> 适用场景：上游发版后 UA / 版本 / 头族对不上（`400 code 11-128`、`code 12403`）、
> 要接新接口、要确认请求体形态（gzip / 紧凑 JSON / 会话头族）。
> 本文只讨论**怎么拿到真实请求**；拿到之后改哪些常量见第 9 节。

---

## 0. 先判断：这次到底要不要抓包

| 想知道的 | 静态就能拿到 | 必须抓包 |
|---|---|---|
| 端点域名、认证头名、平台标识 | ✅ `product.json` | |
| 客户端版本号 | ✅ `install-manifest.json` | |
| 请求头**全集与顺序** | | ✅ |
| 请求体形态（gzip / 紧凑 JSON / 字段集） | | ✅ |
| 会话头族（`X-Conversation-*`）的取值形态与出现条件 | | ✅ |
| SSE 事件序列、429 的 `reset at` 语义 | | ✅ |

先做静态（第 6 节，2 分钟），能省掉一半抓包。

## 1. 本机锚点（Windows，已核实 5.8.4）

| 路径 | 用途 |
|---|---|
| `C:\Program Files\WorkBuddyAI\resources\app.asar.unpacked\cli\product.json` | 端点、`usernameHeader` / `tokenHeader`、域白名单 |
| `C:\Program Files\WorkBuddyAI\resources\install-manifest.json` | `appVersion`（当前 5.8.4）、文件清单 |
| `C:\Program Files\WorkBuddyAI\resources\app.asar` | Electron 主进程 + 渲染进程代码 |
| `C:\Program Files\WorkBuddyAI\resources\app.asar.unpacked\cli\` | 内置 CLI 侧车（`@genie/agent-cli`）——**对话请求是它发的** |
| `C:\Program Files\WorkBuddyAI\resources\vendor\node.zip` | 侧车用的便携 Node（实测 **v22.22.2**，`node-v22.22.2-win-x64/node.exe`） |

macOS 对应位置：`/Applications/WorkBuddy AI.app/Contents/Resources/`。

> **这一条决定抓包方案**：`/v2/chat/completions` 由 Node 侧车发出，不是渲染进程的
> `fetch`。所以「只挂 CDP」抓不到对话请求（见第 5 节的局限）。
>
> **实测补充（2026-10-23）**：本机 5.8.4 客户端**完全不走系统代理**——26 条已建立连接
> 里 18 条直连公网 `:443`、0 条走 `127.0.0.1:7890`。所以「改系统代理」对它无效，
> 想抓客户端本体只能重启并显式传 `--proxy-server`（见 3.8）。

## 2. 三条路线怎么选

| 路线 | 能看到 | 成本 | 什么时候用 |
|---|---|---|---|
| **A. mitmproxy + 强制代理** | 全部，含侧车 | 中（装 CA、强制进程走代理） | 首选；要头族 / body 形态时 |
| **B. CDP attach** | 只有渲染进程的请求 | 低（零证书） | 只看会话列表、msg-center 这类旁路请求 |
| **C. 静态解包** | 常量、端点、UA 公式 | 低 | 每次上游发版先跑一遍 |

## 3. 路线 A（Windows）

### 3.1 装 mitmproxy

```bash
pipx install mitmproxy        # 或 uv tool install mitmproxy
# 也可以直接下 mitmproxy 官方 Windows 安装包
```

### 3.2 起抓包（仓库根目录）

```bash
mkdir -p capture
mitmdump -p 8899 -s tools/capture/wb_capture_addon.py \
    --set wb_out=capture/flows.jsonl
```

插件默认只记 `workbuddy.ai / workbuddy.cn / tencent.com / codebuddy.cn / codebuddy.ai`
的 API 流量，静态资源丢弃，凭据落盘前就被替换。要看完整 body 加
`--set wb_bodies=true`。

### 3.3 信任 CA

首次运行会在 `%USERPROFILE%\.mitmproxy\` 生成证书：

```powershell
certutil -addstore -user Root "$env:USERPROFILE\.mitmproxy\mitmproxy-ca-cert.cer"
```

**关键**：这只让 Chromium / 系统栈认它。Node 侧车用的是自己那套 CA 库，必须额外给：

```powershell
setx NODE_EXTRA_CA_CERTS "$env:USERPROFILE\.mitmproxy\mitmproxy-ca-cert.pem"
```

`setx` 写用户级环境变量，客户端重启后其子进程才会继承。

### 3.4 让流量进代理

1. Windows 设置 → 网络和 Internet → 代理 → 手动设置 `127.0.0.1:8899`
   （Electron 默认读系统代理，渲染进程与主进程都覆盖）。
2. **侧车不会走系统代理**。按可用性依次尝试：
   - **Proxifier / Netch**：规则按进程名 `WorkBuddyAI.exe`、`node.exe` 指向
     `127.0.0.1:8899`，HTTPS 协议。**当前版本只能用这条**——侧车是 Node 22.22.2，
     而 `NODE_USE_ENV_PROXY` 是 Node 24 才有的，环境变量那条路走不通。
   - Clash / Surge 的 TUN + 进程规则把 `*.workbuddy.ai` 导到 mitmproxy。
3. 已经在用 Clash 的话，也可以让 mitmproxy 挂在上游：
   `mitmdump --mode upstream:http://127.0.0.1:7890 -p 8899 -s ...`

### 3.5 触发一次真实对话

新开一个会话，发一句短 prompt，**等流式输出结束**。别复用旧会话——会话头族
（`X-Conversation-ID` / `X-Root-Request-ID`）在首轮才有完整形态。

### 3.6 验证与分析

```bash
python tools/capture/analyze_capture.py capture/flows.jsonl --headers
```

看到 `POST www.workbuddy.ai /v2/chat/completions` 就成功了。

### 3.7 收尾

撤掉系统代理 → 关 mitmdump → 需要的话 `certutil -delstore -user Root <序列号>`
删掉证书。`capture/` 已在 `.gitignore` 里，仍然不要手动提交。

### 3.8 NetLog 抓包（客户端无视代理时的正解，零侵入）

客户端不认 `--proxy-server`、不认系统代理，但 Chromium 自己能把**原始请求头**写进
NetLog。这条路线不装证书、不改 hosts、不动代理，客户端行为与平时一致：

```powershell
# 双击即可
tools\capture\run-capture-netlog.bat

# 或手动指定时长
powershell -ExecutionPolicy Bypass -File tools\capture\capture-netlog.ps1 -Seconds 180
```

脚本：关客户端 → 用 `--log-net-log=capture\netlog.json --net-log-capture-mode=IncludeSensitive`
启动 → 等你发一句话 → 关闭（让 NetLog 落盘）→ `parse_netlog.py` 解析成同一套 JSONL →
跑 `--timeline --coverage --identity`。

要点：

- `--net-log-capture-mode=IncludeSensitive` 才会保留 `Authorization` / `Cookie`；
  默认会写成 `[redacted]`。解析器落盘前仍会替换成 `<redacted:len>`。
- NetLog 只有**请求头 + 响应头 + 状态**，没有请求体（body 仍要靠 3.9 的 hosts 模式）。
- 优雅关闭（`CloseMainWindow`）才能保证 JSON 完整；强杀可能截断。
- **覆盖边界（实测 2026-10-23）**：NetLog 只记录 **Chromium 网络栈**的请求。
  客户端实际打到的只有 `/v2/update`、`/v2/as/users/private-configs/query`、`/` 这类；
  **`/v2/chat/completions` 不出现** —— 对话由 Node 侧车（`cli/dist/codebuddy-headless.js`）
  用 undici 直接发，不经过 Chromium。要抓对话，只能用 3.9 的 hosts 模式。

### 3.9 local 模式（默认，推荐）

mitmproxy 的 `--mode local:<进程名>` 是 **OS 级透明重定向**：按进程名拦截，
不依赖系统代理、hosts 或 DNS。客户端自己解析 IP、复用连接池，也照样被接住。

```powershell
# 默认就是 local 模式，只需要管理员（系统级重定向）
powershell -ExecutionPolicy Bypass -File tools\capture\capture-client.ps1

# 手动回车结束；或指定时长
powershell -ExecutionPolicy Bypass -File tools\capture\capture-client.ps1 -Interactive
powershell -ExecutionPolicy Bypass -File tools\capture\capture-client.ps1 -Seconds 240
```

系统改动只有「信任 CA」（bundle + 当前用户 Root），收尾还原；**不改 hosts、不重启客户端**。

> 为什么它是首选：hosts 方案只覆盖「按 hosts 解析」的连接。实测客户端另有
> 12 条连接自己解析到公网 IP（43.156.86.x 等），`/v2/chat/completions` 正好走这些，
> 所以 hosts 方案能抓到 40+ 个启动接口却抓不到对话。local 模式在 IP 层拦截，
> 这类连接同样会被接住。

### 3.9.1 hosts 模式（备选）

```powershell
# 默认就是 hosts 模式：改 hosts + 反向代理监听 443，上游钉到真实 IP
powershell -ExecutionPolicy Bypass -File tools\capture\capture-client.ps1

# 抓 4 分钟；或手动回车结束
powershell -ExecutionPolicy Bypass -File tools\capture\capture-client.ps1 -Seconds 240
powershell -ExecutionPolicy Bypass -File tools\capture\capture-client.ps1 -Interactive

# 上次异常中断，手动还原 hosts / CA
powershell -ExecutionPolicy Bypass -File tools\capture\capture-client.ps1 -Restore
```

脚本做的事：解析真实 IP → 备份 hosts 与 CA bundle → 追加 mitmproxy CA
→ 起 `mitmdump --mode reverse:https://<域名>@443`（配 `wb_reverse_pin.py` 把上游钉到真实 IP）
→ 写 hosts → 等你发一句话 → 停抓包、还原 hosts / CA → 跑分析。
**全程不碰客户端进程。**

> **必须钉 IP 的原因（踩过的坑）**：hosts 把域名指到 127.0.0.1 之后，反向代理再按域名
> 解析上游就会解析回自己，形成连接回环——日志里是
> `server connect www.workbuddy.ai:443 (127.0.0.1:443)`，客户端所有请求全部失败。
> `dns_use_hosts_file` 只对 regular / wireguard 模式生效，对 reverse 无效，
> 所以只能由外部先解析好真实 IP，交给插件在 `server_connect` 阶段替换地址。

> **CA 的时效**：CA 追加进 `NODE_EXTRA_CA_CERTS` 指向的 bundle，但**已在运行**的侧车
> 进程在启动时已读过旧 bundle。如果客户端开始报网络错误，说明它不认新 CA ——
> 你自己关掉客户端再打开一次即可（脚本不会替你关）。

| 模式 | 原理 | 覆盖 | 权限 | 是否动进程 |
|---|---|---|---|---|
| `hosts`（默认） | hosts + 反向代理 443 + 钉 IP | **全部，含 Node 侧车** | 需管理员 | **否** |
| `proxy` | `--proxy-server=8899` | 渲染进程（实测被强制 DIRECT，无效） | 免管理员 | 需 `-AllowRestart` |

### 3.10 其他工具能不能抓

| 工具 | 能否抓到对话 | 原因 |
|---|---|---|
| Fiddler / Charles / Proxyman | ❌ | 本质都是「让进程走代理」；客户端强制 DIRECT，与 mitmproxy 同一个死因 |
| Proxifier / Netch | ⚠️ | 进程级强制，但注入发生在进程启动时，已在跑的实例要重启才生效 |
| Wireshark / pktmon | ❌ | 能看到 IP/SNI，但 TLS 已加密，拿不到头 |
| Frida attach | ⚠️ | 能挂钩 TLS 写入，无需重启，但侵入性强、可能触发反调试 |
| NetLog | ❌（仅 Chromium 栈） | 见 3.8：只记 Chromium 网络栈，对话走 Node 侧车 |
| **hosts + 反向代理** | ✅ | IP 层重定向，不依赖进程是否 proxy-aware，也不用重启 |

### 3.11 手动版（脚本不适用时）

脚本不适用时（不想提权、只想跑一条命令），手动等价步骤：

1. **解析真实 IP**（必须在改 hosts 之前）：`Resolve-DnsName www.workbuddy.ai -Type A`
2. **追加 CA** 到 `NODE_EXTRA_CA_CERTS` 指向的 bundle，并装进当前用户 Root：
   `certutil -addstore -user Root %USERPROFILE%\.mitmproxy\mitmproxy-ca-cert.cer`
3. **起反向代理**（`wb_reverse_pin.py` 负责把上游钉到真实 IP）：
   `mitmdump --mode reverse:https://www.workbuddy.ai@443 -s wb_capture_addon.py -s wb_reverse_pin.py --set wb_pin_ip=<真实IP> --set wb_pin_sni=www.workbuddy.ai`
4. **写 hosts**：`127.0.0.1 www.workbuddy.ai`，然后 `ipconfig /flushdns`
5. 在客户端发一句话；结束后 `-Restore` 还原 hosts / CA。

> 侧车是 Node 22，不认 `HTTPS_PROXY` / `NODE_USE_ENV_PROXY`；它只认**启动时**读到的
> CA bundle —— 如果抓包期间它报 TLS 错误，需要你自己重启一次客户端（脚本不会替你关）。

## 4. 路线 A（macOS）差异点

```bash
brew install mitmproxy
sudo security add-trusted-cert -d -r trustRoot \
     -k /Library/Keychains/System.keychain ~/.mitmproxy/mitmproxy-ca-cert.pem
networksetup -setsecurewebproxy "Wi-Fi" 127.0.0.1 8899
networksetup -setwebproxy "Wi-Fi" 127.0.0.1 8899
```

侧车同样不认系统代理：`NODE_EXTRA_CA_CERTS=~/.mitmproxy/mitmproxy-ca-cert.pem`
`HTTPS_PROXY=http://127.0.0.1:8899` 写进 `launchctl setenv`，或用 Proxyman
（自带 helper，一键接管非代理感知进程）。

## 5. 路线 B：CDP attach（只覆盖渲染进程）

```powershell
& "C:\Program Files\WorkBuddyAI\WorkBuddyAI.exe" --remote-debugging-port=9222
```

`http://127.0.0.1:9222/json` 拿 `webSocketDebuggerUrl`，连上后 `Network.enable`，
`Network.requestWillBeSentExtraInfo` 能拿到实际发出的头。

**局限**：只有渲染进程发起的请求（会话列表、msg-center、配置拉取）。
`/v2/chat/completions` 是 Node 侧车发的，**不会出现**。用来验证「某个旁路请求改没改」
很省事，但别指望它替代路线 A。

## 6. 路线 C：静态解包（每次发版先跑）

```bash
npx @electron/asar extract "C:\Program Files\WorkBuddyAI\resources\app.asar" /tmp/wb-asar
```

优先看这几处：

```bash
# 端点 / 认证头名 / 域白名单
cat "C:\Program Files\WorkBuddyAI\resources\app.asar.unpacked\cli\product.json"

# 客户端版本
grep -o '"appVersion": *"[^"]*"' "C:\Program Files\WorkBuddyAI\resources\install-manifest.json"

# UA 公式与头常量
grep -rn "buildUserAgent\|X-IDE-Type\|X-IDE-Version" /tmp/wb-asar/ | head
```

`product.json` 里的 `endpoint` / `officialEndpoints` 与
`wb_accounts.REALM_CONFIGS` 的 `chat_upstream` 是同一份事实，**发版先比这里**。

> 没有 `node` / 不想装 `@electron/asar` 时，`app.asar` 可以直接用标准库读：前 16 字节是
> `[4, header_size, ?, json_len]`（小端 uint32），JSON 从 **offset 16** 开始、长 `json_len`；
> 文件数据基址 = `8 + header_size`。本机 5.8.4 实测 `header_size = 3661984`。

## 7. 证书 / pinning 故障判定

| 症状 | 判断 | 处置 |
|---|---|---|
| 浏览器能开 https://www.workbuddy.ai，客户端报网络错误 | 侧车不认 CA | 设 `NODE_EXTRA_CA_CERTS` 后重启客户端 |
| 抓包工具里只有 `CONNECT`，没有解密后的请求 | 客户端没走代理 / 证书未受信 | 查代理是否生效；确认 CA 装在 **当前用户** 的 Root |
| 装完 CA 仍然握手失败，且只有该 App 失败 | 可能做了 pinning | 先确认侧车 Node 是否读到 CA；仍失败则退回路线 C + 只抓渲染进程 |
| 抓到请求但 body 是二进制 | gzip（CLI 身分会压） | 插件已自动解压并记 `gzip: true`；看 `decoded_len` |
| 只抓到渲染进程请求 | 侧车没进代理 | 用 Proxifier 按进程名强制 |
| 上游 `400 code 11-128` | 会话头族缺失 | 对照抓包的 `X-Conversation-ID` / `X-Request-ID` 形态 |
| 上游 `400 code 12403` | UA 不被接受 | 对照抓包 UA，改 `wb_identity.DESKTOP_UA_*` |

## 8. 脱敏红线

插件已自动替换 `Authorization` / `X-API-Key` / `Cookie` / `X-User-Id` /
`machineId` / `sessionId` / 邮箱 / 手机号，但：

- `capture/` 目录**不进版本库**（`.gitignore` 已含），也不要贴到 issue；
- 要分享抓包结论，贴 `analyze_capture.py` 的摘要，不要贴原始 JSONL；
- `--set wb_bodies=true` 会落盘用户 prompt，属于个人数据，用完即删；
- 截图前检查地址栏、账号名、`X-User-Id`。

真 token 抓包的风控评估（IP / 并发 / 设备 token / TLS 指纹）见
`docs/风控校验-5.8.4.md` 第八节。

## 9. 抓到之后改哪里

| 抓到的变化 | 改哪里 |
|---|---|
| `User-Agent` / `X-IDE-Version` | `wb_identity.DESKTOP_UA_INTL` / `DESKTOP_VERSION_INTL`（国内版 `_CN`） |
| 新增 / 消失的请求头 | 请求头族构造处（`wb_proxy.py`）+ `wb_identity` 模块文档串 |
| 新接口路径 | `wb_accounts.py` 顶部的 `*_PATH` 常量 |
| 请求体形态（gzip、字段增删） | `wb_identity` 的请求体处理与 `wb_proxy` 转发分支 |
| 版本号 | `wb_identity` 常量 + README「Unreleased」+ 面板版本显示 |

改完跑：

```bash
python tools/capture/analyze_capture.py capture/flows.jsonl --identity
```

退出码 0 = 抓包与仓库常量一致；1 = 还有漂移（会指出具体常量名）。
