# 客户端接口面 · WorkBuddy 5.8.4（实测）

> 数据来源：2026-10-23 用 `mitmdump --mode local:WorkBuddyAI` 抓的桌面端全量流量，
> 原始文件 `.workbuddy-ai/lifecycle.jsonl`（314 条 flow + 110 条 TLS 握手失败）。
> 本表由 `analyze_capture.py --surface` 生成，可重跑覆盖。

## 五条关键观察

1. **桌面端不调用 `/v2/chat/completions`**。对话走
   `GET /v2/agentos/localagent/workspaces/websocket`（101 Upgrade，Host 是
   `www.codebuddy.ai`）+ `POST /console/as/conversations/{uuid}`，模型调用在服务端完成。
   所以「客户端抓不到 chat」不是抓包问题，是这条路径在桌面端不存在。
2. **最高频的是上报**：`POST /v2/report` 32 次、`/llm/data/report` 16 次、
   `/portal/msg-center/message/summary` 24 次 —— 客户端行为更像「常驻轮询」而不是「一问一答」。
3. **404 是常态**：`/v2/feature-flag/...` 18 次全 404、`/v2/chat/prediction`、`/v2/chat/busy`
   也 404。客户端对这些失败静默，不要拿它们当健康指标。
4. **SSO / 静态资源在别的域**：`tencent.sso.codebuddy.cn`、`download.codebuddy.cn`、
   `static.workbuddy.cn`。仓库不覆盖，也不影响对话鉴权。
5. **原生 SDK 做证书固定**：`sg.tgalileo.com`(33) / `tgalileo.com`(24) /
   `www.workbuddy.ai`(23) / `www.codebuddy.ai`(23) 共 110 次握手失败。
   遥测类抓不到属预期；`www.workbuddy.ai` 那 23 条来自少数非 Node 组件，不影响主链路。

## 与网关的对照

- 网关走 **API 路径**（`/v2/chat/completions`），客户端走 **agent 通道**；
  两者鉴权头族相同（Bearer + `X-User-Id` + `X-Domain`），但端点不同。
- 客户端用 `/v2/plugin/accounts`，仓库用 `/v2/plugin/login/account`（两条都能用）。
- 仓库覆盖的 `/v2/plugin/auth/token/refresh`、`/v3/config`、`/billing/meter/*` 在客户端流量里
  都能看到同源调用，语义一致。
