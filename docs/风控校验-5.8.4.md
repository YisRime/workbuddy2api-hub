# 风控校验报告 · WorkBuddy 5.8.4（2026-10-23）

> 目标：确认网关出站请求与官方桌面端「像不像同一台机器」，以及能不能抓到客户端本体。
> 结论先行，证据在后。

## 一、结论

1. **抓包链路可用**：`客户端 → mitmproxy:8899 → Clash:7890 → 上游` 已实测打通，
   真实上游返回 200 / 401 都被完整抓到（28 个请求头）。
2. **但当前运行中的客户端抓不到**：实测它**完全不走系统代理**——26 条已建立连接里
   18 条直连公网 `:443`，0 条走 `127.0.0.1:7890`；证书信任在进程启动时固定，
   装 Root CA 也不会对它生效。要抓客户端本体**必须重启客户端**（会中断当前会话）。
3. **改用静态提取**（解包 `app.asar` + 内置 CLI `dist`），拿到 5.8.4 真实的头族构造，
   与仓库逐项比对：
   - 会话头族、IDE 三元组、`X-Agent-Intent/Purpose`、id 形态：**与客户端一致**；
   - 仓库多发的 `X-Agent-Type` / `X-Root-Request-ID` / `X-Domain`：客户端 chat 适配器
     不设这三项，但都是官方头名，**低风险冗余**；
   - 客户端声明但 chat 适配器未用的 `X-Session-ID` / `X-Data-Tag` / `X-Product-Version`：
     **不需要补**；
   - `x-requested-with` / `acp-connection-id` / `x-codebuddy-request`：**本地 ACP 网关**的头，
     **不要**加到上游；
   - UA 第二段：chat 路径是 `workbuddy-ai`（仓库一致 ✅），但 main 进程 VLM 路径是
     `WorkBuddy`，**两条路径不同，别照抄**。
4. **边缘先鉴权**：无凭证请求在 APISIX 就被 401 拦下，`code 11-128`（会话头缺失）这类
   指纹门禁**只在鉴权通过后**才触发——所以「无凭证探针」验不了指纹，必须带真 token
   或抓客户端本体。

## 二、证据链

### 2.1 为什么 mitmproxy 一条也抓不到（2026-10-23 实测）

带 `--proxy-server=http://127.0.0.1:8899` 重启客户端后：

- 客户端自己的日志：`POST https://sg.tgalileo.com/v1/logs -> DIRECT (status=200)`
  —— 每条都标 **DIRECT**；
- `netstat`：客户端仍在直连公网 `:443`，**没有任何一条连接到 127.0.0.1:8899**；
- 结果：mitmdump 收到 0 条流量，`lifecycle.jsonl` 根本没被创建。

结论：这个版本的客户端在代码里强制直连（Electron `setProxy` direct 或自带网络栈），
`--proxy-server` 被覆盖。**不是 CA 问题，也不是脚本问题。**

### 2.1b NetLog 也只覆盖一半（2026-10-23 实测）

改用 Chromium NetLog（`--log-net-log` + `--net-log-capture-mode=IncludeSensitive`）后，
747 KB 的 netlog 里 `workbuddy.ai` 出现 112 次，但 URL 只有这些：

```
30  https://www.workbuddy.ai
15  https://www.workbuddy.ai/v2/update
 3  https://www.workbuddy.ai/v2/as/users/private-configs/query
 3  https://workbuddy.ai
```

**没有 `/v2/chat/completions`**，也没有鉴权/配置接口。原因：NetLog 只记 Chromium 网络栈；
对话由 Node 侧车（`cli/dist/codebuddy-headless.js`，undici）直接发出，不经过 Chromium。

→ 抓对话只剩一条路：**IP 层重定向**（hosts + mitmproxy 反向代理监听 443），
它不依赖进程是否 proxy-aware，侧车的 TCP 连接同样会被接住。

## 三、逐项比对

客户端侧代码位置：`app.asar!main/server.js`（ACP/主进程）、
`cli/dist/codebuddy-headless.js`（真正发 chat 的 CLI 适配器）。

| 头 | 客户端 chat 适配器 | 仓库 desktop | 判定 |
|---|---|---|---|
| `X-Conversation-ID` | ✅ `session.id` | ✅ | 一致 |
| `X-Conversation-Request-ID` | ✅ | ✅ | 一致 |
| `X-Conversation-Message-ID` | ✅ | ✅ | 一致 |
| `X-Request-ID` | ✅ 与 messageId 同值 | ✅ | 一致 |
| `X-Agent-Intent` | ✅ `craft`（或会话 mode） | ✅ `craft` | 一致 |
| `X-Agent-Purpose` | ✅ `conversation` | ✅ | 一致 |
| `X-IDE-Type` / `X-IDE-Name` | ✅ 来自 `telemetryClientInfo` | ✅ `WorkBuddy` | 一致 |
| `X-IDE-Version` | ✅ | ✅ `5.8.4` | 一致 |
| `User-Agent` | ✅ `platform/productName/extension` | ✅ `WorkBuddy/5.8.4 workbuddy-ai/5.8.4 CLI/2.161.0` | 一致 |
| `X-Agent-Type` | ⚠️ 本片段未设（子代理路径才有） | 发 `main` | **低风险冗余** |
| `X-Root-Request-ID` | ⚠️ 主对话不设 | 发 | **低风险冗余** |
| `X-Domain` | 上层拦截器设置（本片段未覆盖） | 发 | 未覆盖，保持 |
| `X-Private-Data` / `X-Product` / `X-User-Id` / `Authorization` | 上层拦截器设置 | 发 | 未覆盖，保持 |
| `traceparent` | ✅ CLI 用 OTel 注入 | ✅ | 一致 |
| `b3` / `X-B3-*` | ⚠️ main 进程用 B3；CLI 走 OTel | CLI 分支也发 B3 | **可能多余**，低风险 |
| `X-Session-ID` | 仅声明常量，chat 适配器未用 | 不发 | 不需要补 |
| `X-Data-Tag` / `X-Product-Version` | 仅声明常量 | 不发 | 不需要补 |
| `x-requested-with` / `acp-connection-id` / `x-codebuddy-request` | **本地 ACP 网关**请求 | 不发 | **正确，别加** |

id 形态（实锤，`codebuddy-headless.js` 的 `axiosToFetchAdapter`）：

- `messageId = uuid().replace(/-/g,"")` → **32 位无连字符 hex**，`X-Request-ID` 与
  `X-Conversation-Message-ID` 同值 —— 与仓库 `new_message_id()` 一致；
- `X-Conversation-ID` = 会话 id（同一会话恒定）—— 与仓库 CLI 分支的
  `conversation_id_for()` 语义一致，桌面端分支「每请求新生成」与客户端不同，
  但上游不据此存历史（仓库注释已记录该实测），影响仅限「像不像」。

| 级别 | 项 | 建议 |

### 三个结论

1. **桌面端根本不调用 `/v2/chat/completions`**。对话走 `agentos/localagent` 的
   WebSocket + `/console/as/conversations/{uuid}`，真正的模型调用在**服务端**完成。

2. 网关的 desktop 身份**仍然有效**：`/v2/chat/completions` 对 API 侧开放（实测 401/200），

3. 仓库没覆盖的域：`tencent.sso.codebuddy.cn`（SSO）、`download.codebuddy.cn`（插件市场）、
   `galileotelemetry.tencent.com`（遥测）。这三类不参与对话鉴权，不需要跟。

## 五、要闭环还差什么
一次**带真 token 的客户端全生命周期抓包**，用于验证鉴权之后的那道指纹门禁
（`code 11-128` / `12403`），同时把「启动 → 登录 → 配置 → 会话 → 退出」整条链路的
请求序列和网关逐条对上。

现成脚本（会重启客户端，当前对话会中断）：

```powershell
tools\capture\run-capture-netlog.bat        # 零侵入：Chromium NetLog，不装 CA/不改 hosts
powershell ... capture-client.ps1 -Mode hosts  # 要请求体时：hosts + 反向代理
```

跑完自动出三份结果：

```bash
python tools/capture/analyze_capture.py capture/lifecycle.jsonl --timeline   # 生命周期时序
python tools/capture/analyze_capture.py capture/lifecycle.jsonl --coverage   # 客户端 vs 网关接口
python tools/capture/analyze_capture.py capture/lifecycle.jsonl --identity   # 常量漂移
```

`--coverage` 会直接列出「客户端有、网关没有」和「网关有、静态提取未在客户端发现」两组，
这就是「逻辑不同」的清单。手动版步骤见 `docs/抓包指南.md` 第 3.8 / 3.9 节。

**注意：重启客户端会中断当前对话。**

`WxAuthenticationProvider`、`ProductEndpointHttpInterceptor`、`axiosToFetchAdapter`）：

| # | 阶段 | 客户端做什么 | 端点 / 头 | 仓库现状 |
|---|---|---|---|---|
| 1 | 设备与客户端信息 | qimei / TuringShield 原生 SDK 产设备 token；clientInfo = ideType / platform / version | `X-Device-Token`；UA 由 `buildUserAgent` 拼 | ✅ 国内版发真 token；国际版按官方不发；拿不到 SDK 时发 `X-Device-Token-Error: sdk_not_initialized` |

| 3 | 拉账号列表 | 取 `accounts`，只留 `pluginEnabled` | `GET /v2/accounts`（Bearer + `X-Domain` + 企业头） | ❌ 未实现（网关自己维护号池，语义上不需要） |

| 6 | 会话与轮次 id | conversation / request / message id | 头族 | ✅ |
| 7 | 计量与签到 | 配额、资源包、签到 | `/billing/meter/*` | ✅ |

真正还有未知的是第 1 步：原生 SDK 在 MITM 下会不会失败（见下一节）。

## 八、用真 token 抓包会不会触发风控

**先看一个既有事实**：网关每天用 Python/OpenSSL 的 TLS 栈冒充 Node/BoringSSL 的桌面端，
JA3/JA4、HTTP/2 SETTINGS 全不一样，号池里的账号照跑（本机健康检查：17 个号）。
这说明上游**没有把 TLS 指纹当硬门禁**，否则网关早就挂了。所以 mitmproxy 抓包的风险不会
比网关日常更高。

| 风险 | 机制 | 严重度 | 缓解 |
|---|---|---|---|
| 出口 IP 变化 | 链到 Clash，节点一切换就是「同 token 换 IP」 | **中** | 抓包期间锁死节点；能直连就直连 |
| 同 token 并发 | 网关与客户端同时用同一账号、两套 TLS 栈 | **中** | 抓包前停网关或换一个号 |
| 设备 token 失效 | 原生 SDK 若做了 pinning，MITM 下拿不到 token → 请求带 `X-Device-Token-Error` | **中** | 优先抓渲染进程旁路请求；或接受这次差异 |
| TLS / h2 指纹差异 | OpenSSL vs BoringSSL | 低（见上） | 保持 h2，不改 UA / body |
| 批量或重放 | 反复重放历史请求、并发轰炸 | **高** | 只发 1 条真实提问，不重放 |

**结论**：单次、同 IP、同账号、发一条真实提问 → 触发账号级风控的概率很低。
要避免的是「同 token 多 IP 并发」和「批量重放」，这两条才是真正的关联/滥用信号。
另外抓包会把真 token 写进 flow（插件已在落盘前替换成 `<redacted:len>`），
但 `--set wb_bodies=true` 仍会记录 prompt 正文，用完即删。
