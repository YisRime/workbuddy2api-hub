## 2. 已验证的结论（按可信度排序，全部有实测）

### 2.1 客户端不认任何「代理」配置

| 手段 | 结果 | 证据 |
|---|---|---|
| 系统代理（HKCU Internet Settings） | ❌ 无效 | 26 条连接里 18 条直连公网 `:443`，0 条走 `127.0.0.1:7890` |
| `--proxy-server` 启动参数 | ❌ 无效 | 客户端日志逐条 `-> DIRECT`，`netstat` 无任何到 8899 的连接 |
| CDP attach | ❌ 只覆盖渲染进程 | 对话由 Node 侧车发出 |
| Chromium NetLog | ❌ 只覆盖 Chromium 栈 | 747 KB 里只有 `/v2/update`、`/v2/as/users/private-configs/query`、`/` |

### 2.2 能抓到的方式：mitmproxy `local` 模式（推荐）

```
mitmdump -p 8899 --mode local:WorkBuddyAI -s wb_capture_addon.py --set wb_out=... 
```

- `local` 是 **OS 级透明重定向**（`mitmproxy_rs.local.LocalRedirector`，Windows 支持），
  按**进程名**拦截，不依赖代理 / hosts / DNS。客户端自己解析 IP、复用连接池也能接住。
- spec 语法：`local`（全部）、`local:curl`（进程名）、`local:42`（PID）、`local:!curl`（取反）、
  逗号分隔多目标。程序名只匹配前 16 字符（内核限制，Linux 侧）。
- 需要管理员。系统改动只有「信任 CA」。

备选：`hosts + 反向代理 443`（`-Mode hosts`）。缺点：只覆盖按 hosts 解析的连接，
实测漏掉 12 条自解析 IP 的连接（对话正好走这些），所以**只作为备选**。

### 2.3 桌面端不调用 `/v2/chat/completions`（最重要）

实测 301 条 flow，客户端真实接口面（节选）：

| 接口 | 次数 | 状态 |
|---|---|---|
| `POST /v2/plugin/auth/token/refresh` | 2 | 200 |
| `GET /v2/plugin/accounts` | 2 | 200（仓库用的是 `/v2/plugin/login/account`） |
| `GET /v3/config` | 6 | 200 |
| `POST /billing/meter/get-user-resource-*` | 6 | 200 |
| `GET /console/as/conversations/` | 4 | 200 |
| `POST /console/as/conversations/{uuid}` | 3 | 200（uuid = 当前会话） |
| `POST /space/api/agent/v1/mcp` | 13 | 200/202 |
| `GET /v2/agentos/localagent/workspaces/websocket` | 1 | **101 Upgrade** |
| `POST /v2/agentos/localagent/registerWorkspace` | 2 | 200 |
| `POST /edge-cloud/credentials` | 2 | 200 |
| `GET /api/memory/profile` | 3 | 200 |
| `GET /api/v2/open-platform/buddy/entrance`（`tencent.sso.codebuddy.cn`） | 17 | 401 |
| `GET /v2/feature-flag/api/feature-flags/check` | 12 | 404（客户端自己忽略） |

WebSocket 握手的**真实头**（几乎没有 X-IDE 家族）：

```
GET /v2/agentos/localagent/workspaces/websocket  → 101
Host: www.codebuddy.ai
Connection: Upgrade / Upgrade: websocket
Sec-WebSocket-Version: 13 / Sec-WebSocket-Key: …
Sec-WebSocket-Extensions: permessage-deflate; client_max_window_bits
```

结论：
1. 对话走 `agentos/localagent` 的 WebSocket + `/console/as/conversations/{uuid}`，
   **模型调用在服务端完成**，客户端不发 chat 请求。之前所有「抓不到 chat」都不是抓包失败。
2. 网关的 desktop 身份**仍然有效**：`/v2/chat/completions` 对 API 侧开放（实测无凭证 401、
   带假 token 401，说明 APISIX 先鉴权），对齐目标是「API 契约」而非「客户端实际流量」。
3. 仓库没覆盖的域：`tencent.sso.codebuddy.cn`（SSO）、`download.codebuddy.cn`（插件市场）、
   `galileotelemetry.tencent.com`（遥测）。不参与对话鉴权，不需要跟。

### 2.4 风控评估

- **TLS 指纹不是硬门禁**：网关日常用 Python/OpenSSL 冒充 Node/BoringSSL，号池照跑 →
  上游不靠 JA3 拦。mitmproxy 抓包的风险不高于网关日常。
- 真风险是「同 token 换 IP」「同 token 并发两套栈」「批量重放」，不是单次抓包。
- 客户端有原生 SDK 做证书固定（tgalileo、codebuddy.ai 下载域，实测 88 条 TLS 握手失败），
  这类流量抓不到也不影响结论。

### 2.5 客户端会话前链路（8 步，来自代码提取）

设备 token(qimei) → `/v2/auth/token/wxide` 换 token → `GET /v2/accounts` →
`/v2/auth/token/refresh`（头 `X-Refresh-Token` + `X-Auth-Refresh-Source`）→
`/v3/config` → 会话 id → billing meter → `/v2/spans` 遥测。
仓库覆盖 1/2/4/5/6/7；缺 `/v2/accounts`（不需要）与 `/v2/spans`（可观测性差异，非鉴权）。

### 2.6 头族比对（静态提取 5.8.4）

| 项 | 结论 |
|---|---|
| 会话头族 / IDE 三元组 / `X-Agent-Intent`·`Purpose` | 与客户端一致 |
| id 形态（messageId = uuid 去连字符 32hex） | 一致 |
| UA 第二段 `workbuddy-ai`（chat 路径） | 一致；主进程 VLM 路径是 `WorkBuddy/WorkBuddy`，别照抄 |
| 仓库多发 `X-Agent-Type` / `X-Root-Request-ID` | 低风险冗余 |
| `x-requested-with` / `acp-connection-id` / `x-codebuddy-request` | 本地 ACP 网关的头，**不能加到上游** |
| `X-Session-ID` / `X-Data-Tag` / `X-Product-Version` | 仅声明常量，chat 适配器未用，不用补 |

## 4. 必须保留的实现细节（踩过的坑，重建时照抄）

### 4.1 抓包记录 schema（JSONL）

```json
{"kind":"flow","ts":1792765516.13,"host":"www.workbuddy.ai","method":"POST",
 "path":"/v2/chat/completions","path_tpl":"/v2/chat/completions","status":401,
 "req_headers":[["Host","www.workbuddy.ai"],["Authorization","Bearer <redacted:11>"]],
 "req_body":{"len":33,"json":true,"keys":["messages","model"]},
 "resp":{"status":401,"content_type":"text/html; charset=utf-8","len":251}}
```

- 头用 **`[[name, value], …]`**（保留大小写与顺序，dict 会丢）；
- 脱敏：`Authorization/X-API-Key/Cookie/X-User-Id/X-Machine-Id…` → `<redacted:len>`，
  body 里 `token/secret/uid/machineId/sessionId/email/phone` 递归替换；
- `path_tpl`：UUID→`{uuid}`、32hex→`{hex32}`、≥5 位数字→`{n}`；
- **SSE 绝不读 body**：`resp.stream = True` + 只记 `content-length`，
  否则 mitmproxy 会把整段流缓冲下来，客户端首字延迟崩掉；
- 另有 `kind:"tls_fail"`（客户端不认 CA 的证据）与 `websocket_start` 钩子（记 101 握手头）。

### 4.2 分析器能力

```
python tools/capture/analyze_capture.py <jsonl> [--headers] [--timeline] [--coverage] [--diff BASE] [--identity]
```

- `--identity`：抓包 UA/版本 vs `wb_identity` 常量，漂移时点名常量并退出码 1；
- `--coverage`：`CLIENT_PATHS`（客户端实测接口）vs `repo_paths()`（从 `wb_accounts`/`wb_proxy`
  的 `*_PATH` 常量导入，失败退回正则扫源码），输出「客户端有网关无」「网关有客户端未发现」；
- `--timeline`：按 ts 排序打印整条生命周期。

### 4.3 hosts 模式的两个致命坑（如果重建 hosts 模式）

1. **DNS 回环**：hosts 把域名指到 127.0.0.1 后，反向代理按域名解析上游又解析回自己
   （日志 `server connect www.workbuddy.ai:443 (127.0.0.1:443)`）。
   `dns_use_hosts_file` 只对 regular/wireguard 生效，**对 reverse 无效**。
   → 外部先解析真实 IP，插件在 `server_connect` 里 `server.address = (ip, 443)`、`server.sni = 域名`。
2. **请求行变 IP**：只钉地址会让 mitmproxy 用 IP 拼请求行（`POST https://43.x/...`），
   上游按 Host 路由直接 404。→ 再在 `requestheaders` 里把 `Host` 与 `request.host` 拉回域名。

### 4.4 NetLog 解析

`--log-net-log=<file> --net-log-capture-mode=IncludeSensitive`（不加第二个参数头会被写成 `[redacted]`）。
事件名在 `constants.logEventTypes` 里是**数字 id**，需要反查；关注
`URL_REQUEST_START_JOB` / `HTTP_TRANSACTION_SEND_REQUEST_HEADERS` / `..._READ_RESPONSE_HEADERS`，
事务事件没有显式父链，按时间就近归到最近一条还没配头的请求。

### 4.5 脚本行为约定（用户明确要求）

- **默认不关闭、不重启客户端**；只有 `-Mode proxy` 与 NetLog 模式在显式 `-AllowRestart` 时才动进程；
- 收尾 `finally` 里只做三件事：停 mitmdump、还原 hosts、还原 CA bundle + 删 Root 证书；
- CA 追加到 `NODE_EXTRA_CA_CERTS` 指向的 bundle（本机 `~/.workbuddy-ai/system-ca-bundle.pem`）；
- **顺序要求**：先起脚本（装 CA），再启动客户端 —— 侧车在**进程启动时**读 bundle，
  晚装 CA 的进程不认（日志 `Client TLS handshake failed`）。
