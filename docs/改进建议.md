# 改进建议（按投入产出排序）

> 结论先放前面：这个项目的功能密度已经很高，**短板不在功能，在「可维护性」和
> 「上游契约的自动核对」**。前者决定还能加多少功能，后者决定上游发版时会不会静默降级。
> 下面每条都给了现状证据、动作和验收标准，可以直接切成 PR。

## 现状数字（本次实测）

| 指标 | 数值 | 说明 |
|---|---|---|
| `wb_proxy.py` | 23,026 行 / 776 个 def | `Handler.do_GET` 单函数 3,388 行（18647–22035），`do_POST` 923 行 |

| `dashboard.html` | 988 KB 单文件 | 无构建、无模块拆分 |

## P0 — 先做这三件

### 1. 上游指纹漂移检测（本次已落地一半）

**问题**：`wb_identity.py` 的 UA / 版本是**人工抓包后手写**的常量（`5.8.4` 对应
2026-10-16 的抓包）。上游一发版，网关不会报错，只会静默降级：模型列表少几条、
`12403` 偶发、某些请求被降级到别的渠道。没有任何机制告诉你「该重新抓包了」。

**已做**：

- `tools/capture/wb_capture_addon.py`：mitmproxy 插件，落盘前脱敏，只留请求形状；
- `tools/capture/analyze_capture.py`：摘要 / 两次抓包 diff / 与 `wb_identity` 常量核对；
- `docs/抓包指南.md`：三条抓包路线（含「侧车不走系统代理」这个必踩的坑）；
- `tests/_test_capture_tools.py`：12 项断言钉住脱敏与 diff 行为。

**还差**：

- 把一次脱敏后的抓包存成 `tests/fixtures/upstream-intl.jsonl`（只含形状，无凭据），
  加一个 `_test_identity_fixture.py`：断言「fixture 里的 UA/版本 == 当前常量」。
  上游一改版，这个套件立刻红，比任何监控都直接。
- README「Unreleased」里补一条，说明重抓包的触发条件。

**验收**：改 `DESKTOP_UA_INTL` 一个字符 → 套件红，且报错信息直接指出常量名。

### 2. 结构化日志 + 一个 `/metrics`

**问题**：71 处 `print` 全打到 stdout，`console_tail.py` 只能按行 grep。线上排障的
实际路径是「翻控制台找那一行」，而 196 个宽 `except` 把真正的原因也吞成了同一行文本。

**动作**（不违反纯标准库）：

1. 引入 `logging` + 一个 `JsonLineFormatter`：`ts / level / event / account / model /
   status / upstream_code / latency_ms / req_id`；
2. `print` 逐个换成 `log.info("event=...", extra={...})`，**先换上游请求相关的 20 处**
   （chat 转发、token 刷新、429、限流窗口），其余保持不动；
3. 加 `/metrics`（纯文本 Prometheus 格式，不引依赖）：每账号成功/失败数、429 计数、
   首字节 P50/P95、上游错误码分布、在飞请求数。

**验收**：一次失败请求能在日志里按 `req_id` 串起「选了哪个号 → 上游返回什么 →
重试到哪个号」；`/metrics` 的 429 计数与面板数字一致。

### 3. `wb_proxy.py` 渐进拆分

**问题**：23k 行单文件，`do_GET` 一个函数 3,388 行。任何改动都要在 3 千行里找位置，
冲突率极高（639 个 PR 的仓库，这点会持续放大）。

**动作**（每次一个 PR，行为不变，测试钉住）：

1. 抽 `wb_http.py`：`Handler` 基类 + 路由表（`(method, 前缀) -> 函数`），先把
   `do_GET` 里的 if 链换成表驱动，**不搬业务代码**；
2. 抽 `wb_chat.py`：`open_upstream` + 重试/换号/亲和这一段（现在在 14k 行附近）；
3. 抽 `wb_panel.py`：面板静态资源与设置接口。

**验收**：每步 `python tests/run_all.py` 全绿；`wb_proxy.py` 行数每步下降 ≥ 15%；
对外行为零变化（对比同一批请求的响应字节）。

## P1 — 值得做，但不急

### 4. 静态检查（dev-only）

加 `requirements-dev.txt`（ruff + mypy）与 `pyproject.toml`，CI 只跑一条腿：

```toml
[tool.ruff]
select = ["E9", "F63", "F7", "F82", "B006", "B008"]   # 先只开「一定是 bug」的规则
```

先只开「未定义名 / 语法 / 可变默认参数」这类零误报规则，再逐步加。别一上来开全量——
2000 条告警会把 PR 淹没。

### 5. 配置项集中声明

81 个 `WB_*` 散落在 20 多个文件里，没有类型、没有默认值清单、没有校验。建议
`wb_config.py`：`{名称: (类型, 默认值, 说明, 生效时机)}`，面板「设置」页与
`--print-config` 都从这张表生成。顺带解决「文档写了但代码没实现 / 代码实现了文档没写」。

### 6. README 拆分

608 行 138 KB，最长一行 3,274 字符。拆成 `docs/配置.md`、`docs/部署.md`、
`docs/FAQ.md`、`docs/接口.md`，README 只留索引 + 快速启动 + 更新记录。
注意：仓库有测试钉住「N 个套件」的计数文案，拆完同步。

顺带可清：`### 6. 测试` 段里堆了 11 行历史计数（209 / 211 / 211 / … / 225），
是多次合并各自追加留下的，只保留最新一行即可（测试只要求「存在一行正确值」，
所以这些残留一直没被发现）。

### 7. 测试分层

233 个套件全量跑一遍成本不低。给 `run_all.py` 加 `--fast`（按文件内的
`SMOKE = True` 标记或文件名清单挑 30 个核心套件）：PR 走 fast，合并到 main 跑全量。

## 明确不建议做的事

1. **不要大爆炸重写 `wb_proxy.py`**。639 个 PR 的仓库，重写的冲突成本远高于收益。
2. **不要为了「对齐」把 UA / 版本常量复制到多处**。历史上 intl 那份就漏改过
   （`wb_accounts.REALM_CONFIGS` 的注释里写着）。单一事实源只能是 `wb_identity`。
3. **不要把抓包产物提交进仓库**，即使已脱敏。`capture/` 已加入 `.gitignore`。
4. **不要用改测试来消红**。这是 CONTRIBUTING 第 3 节的硬规矩。
